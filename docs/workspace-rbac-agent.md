# Aivory 工作空间 RBAC 改造方案

> 本文档用于指导后续智能体分析、完善和实施 Aivory 的工作空间权限系统。实施前必须重新阅读当前代码，不能仅依据本文档假设实现未发生变化。

## 1. 设计结论

Aivory 不在工作空间内部增加部门、协作组或其他分域层级。

原因：

- 工作空间本身就是资源和成员的隔离域。
- 需要隔离不同团队、部门、客户或项目时，可以创建多个工作空间。
- 再增加协作组会重复工作空间已有能力。
- 协作组会显著增加对话、项目、知识库、文件、RAG、沙盒和工具调用的授权复杂度。
- Aivory 的主要定位是个人和中小团队，不需要企业级多层组织树。

最终权限边界：

```text
账号
├── 个人空间
├── 工作空间 A
│   ├── 私有资源
│   └── 工作空间共享资源
├── 工作空间 B
│   ├── 私有资源
│   └── 工作空间共享资源
└── 工作空间 C
```

不同工作空间之间必须完全隔离。工作空间内部只区分私有和共享，不再增加第三层范围。

## 2. 目标

- 工作空间内部只保留三个用户可见角色：`admin`、`member` 和 `guest`。
- 工作空间创建者自动成为工作空间所有者和管理员。
- 所有者可以将成员或游客提升为管理员。
- 游客是已登录并加入工作空间的只读角色。
- 不增加协管员、自定义角色或第四种角色。
- 不增加协作组、部门、团队组或项目域。
- 工作空间本身承担分域作用。
- 资源只使用 `private` 和 `workspace` 两种可见范围。
- 权限模型轻量、明确、可解释、可测试。
- 个人空间行为保持不变。
- 平台管理员和平台用户组不属于本文档范围。
- 权限降低、退出或被移除后必须立即生效。
- 保留现有工作空间撤权、事务锁、流式生成终止和知识库安全逻辑。

## 3. 非目标

本方案不包含：

- 平台管理员 RBAC。
- 平台用户组和套餐权限重构。
- 工作空间第四种角色。
- 自定义角色和角色模板。
- 协作组或部门层级。
- 一个资源授权给指定成员列表。
- 显式拒绝规则。
- 企业组织树。
- 跨工作空间资源共享。
- 跨工作空间统一知识库。
- 单独为每一种文件建立权限表。

## 4. 核心概念

### 4.1 三个角色

```text
admin   工作空间管理员
member  工作空间成员
guest   工作空间游客，只读
```

角色决定用户在当前工作空间内能做什么。

### 4.2 所有者不是第四种角色

`workspaces.owner_id` 表示唯一的工作空间所有者。

所有者：

- 创建工作空间时自动产生。
- 工作空间角色始终为 `admin`。
- 不能被降级为 `member` 或 `guest`。
- 不能被其他管理员移除。
- 不能直接退出工作空间。
- 可以删除工作空间。
- 可以转移所有权。
- 可以提升、降级或移除其他管理员。

普通管理员也是 `admin`，但不能执行所有者专属操作。

### 4.3 工作空间就是域

如果一个组织需要隔离研发和市场资源，应创建两个工作空间：

```text
研发工作空间
市场工作空间
```

如果需要隔离不同客户，应创建：

```text
客户 A 工作空间
客户 B 工作空间
```

用户可以加入多个工作空间，但在每个工作空间中的角色和资源完全独立。

### 4.4 资源创建者不是角色

对话、项目和知识库保留创建者字段，用于：

- 审计资源来源。
- 允许普通成员管理自己创建的资源。
- 识别成员退出后的资源接管行为。

创建者不能绕过工作空间成员关系。用户退出或被移除后，即使资源由其创建，也不能继续访问。

截至本文档编写时：

- 个人空间与工作空间通过 `workspace_id` 隔离。
- 工作空间角色主要使用 `owner/member`，目前没有 `guest`。
- 工作空间创建者同时存在于 `owner_id` 和成员表中。
- 普通成员拥有 5 个布尔权限。
- 工作空间对话支持创建者私有或全体成员公开。
- 工作空间项目和知识库默认对全体成员共享。
- 工作空间成员退出或被移除时会撤销访问。
- 进行中的生成会在成员撤销时终止。
- 知识库已经存在成员总权限和单知识库覆盖权限。
- 当前没有所有权转移。
- 当前邀请主要依赖一个工作空间通用令牌。
- 项目和部分对话 mutation 的修改边界比删除边界宽。

## 6. 权限模型

### 6.1 管理员权限

管理员可以：

- 查看工作空间全部资源，包括其他成员的私有资源。
- 修改工作空间名称和设置。
- 创建成员或游客邀请。
- 查看和管理成员与游客。
- 移除成员或游客。
- 修改成员能力限制。
- 在 `member` 和 `guest` 之间调整普通用户角色。
- 配置工作空间允许使用的模型、工具、MCP、沙盒和图片能力。
- 查看工作空间用量和成员用量。
- 创建、查看、修改和删除全部工作空间资源。
- 将资源从私有改为共享，或从共享改为私有。

只有所有者可以：

- 删除工作空间。
- 转移工作空间所有权。
- 创建管理员邀请。
- 将成员或游客提升为管理员。
- 将管理员降级为成员。
- 移除普通管理员。

### 6.2 成员权限

成员可以：

- 进入当前工作空间。
- 查看工作空间共享资源。
- 查看自己的私有资源。
- 使用当前工作空间允许的模型、工具、MCP 和沙盒。
- 在共享对话中继续发送消息。
- 管理自己创建的对话、项目和知识库。
- 删除自己发送的对话轮次。
- 删除自己上传的知识库文档和文件。
- 根据成员能力限制创建项目、知识库和私有对话。

成员不可以：

- 修改工作空间设置。
- 管理邀请。
- 管理其他成员。
- 修改其他成员创建的资源元数据。
- 删除其他成员创建的资源。
- 删除其他成员上传的内容。
- 修改工作空间模型、工具或费用策略。
- 提升自己或其他成员为管理员。

### 6.3 游客权限

游客是只读角色。游客必须登录并通过邀请加入工作空间，不是匿名访问者。

游客可以：

- 进入当前工作空间。
- 查看工作空间共享对话及其已有消息。
- 查看工作空间共享项目的基本信息、指令和已有内容。
- 查看工作空间共享知识库的基本信息、文档列表和文档预览。
- 查看或下载共享资源中已经存在的附件和产物。
- 查看允许公开给工作空间成员的成员昵称、头像和角色。

游客不可以：

- 查看任何成员的私有资源。
- 发送消息或继续已有对话。
- 调用任何模型。
- 发起知识库 RAG 检索或查询改写。
- 使用内置工具、MCP、Python 沙盒或图片生成。
- 创建对话、项目或知识库。
- 上传、粘贴、替换、重试或删除任何文件。
- 修改、分享、归档、固定或删除任何资源。
- 修改个人以外的工作空间状态。
- 查看工作空间费用、用量、邀请链接或成员邮箱。

游客权限固定为只读，不显示成员能力开关。

### 6.4 成员能力限制

成员能力限制不是新角色，只用于对单个成员进一步收紧能力。

建议保留：

```text
can_create_projects
can_private_conversations
can_create_kb
can_add_kb_files
can_delete_own_content
```

建议迁移或废弃：

```text
can_delete_kb_content
```

普通成员不能因为一个布尔开关获得删除其他成员知识库内容的权限。

管理员不受成员能力限制影响。

### 6.5 有效权限公式

```text
有效权限 =
当前工作空间成员关系
∩ 角色基础权限
∩ 工作空间允许范围
∩ 当前成员能力限制
∩ 资源可见范围
∩ 资源创建者规则
```

`guest` 必须额外满足只读限制。即使某个接口只读取数据，只要该操作会产生模型、Embedding、Rerank、搜索、工具或沙盒调用，也不属于游客只读权限。

所有者专属操作必须额外验证：

```text
workspaces.owner_id == current_user_id
```

## 7. 资源可见范围

只保留两种：

```text
private    创建者和管理员可见
workspace  当前工作空间管理员、成员和游客可见
```

可以继续使用现有 `is_public`，也可以统一迁移为：

```sql
visibility TEXT NOT NULL DEFAULT 'private'
```

如果为了减少数据库改动，第一阶段可以保留：

```text
is_public = 0  -> private
is_public = 1  -> workspace
```

项目和知识库建议补充同样的可见范围字段。如果希望保持当前体验，可以默认：

```text
新建工作空间对话 -> private
新建工作空间项目 -> workspace
新建工作空间知识库 -> workspace
```

成员可以把自己创建的资源改为共享或私有。管理员可以修改任意资源范围。游客不能创建资源，也不能修改资源范围。

## 8. 文件继承规则

文件不单独设计可见范围，直接继承所属资源：

| 文件类型 | 权限来源 |
|---|---|
| 对话附件 | 对话 |
| 对话沙盒产物 | 对话 |
| 对话生成图片 | 对话 |
| 项目上传文件 | 项目 |
| 项目知识库文档 | 项目 |
| 独立知识库文档 | 知识库 |

如果文件没有所属工作空间资源，则继续按照个人空间文件规则处理。

## 10. 统一授权器

必须建立统一的后端授权入口，避免 handler 和 store 分别实现不同规则。

建议结构：

```go
type WorkspaceAuthorizationRequest struct {
    WorkspaceID string
    UserID      string
    Action      string
    Resource    string
    ResourceID  string
}

type WorkspaceAuthorizationDecision struct {
    Allowed    bool
    IsOwner    bool
    IsAdmin    bool
    IsCreator  bool
    IsPublic   bool
    Reason     string
}
```

建议入口：

```go
func AuthorizeWorkspace(
    ctx context.Context,
    db *sql.DB,
    req WorkspaceAuthorizationRequest,
) (WorkspaceAuthorizationDecision, error)
```

建议 action：

```text
workspace.settings.update
workspace.member.view
workspace.member.invite
workspace.member.remove
workspace.member.permissions.update
workspace.member.role.update
workspace.delete
workspace.transfer

conversation.create
conversation.read
conversation.reply
conversation.metadata.update
conversation.visibility.update
conversation.delete

project.create
project.read
project.update
project.visibility.update
project.delete

knowledge_base.create
knowledge_base.read
knowledge_base.document.add
knowledge_base.document.delete_own
knowledge_base.document.delete_any
knowledge_base.update
knowledge_base.visibility.update
knowledge_base.delete

model.use
tool.use
mcp.use
sandbox.use
image.generate

usage.view

```

授权器必须默认拒绝。数据库错误、角色异常、资源状态异常时不能 fail-open。

前端返回的 `can_xxx` 只能用于界面展示，后端 mutation 必须在事务内重新授权。

## 11. 邀请系统

建议使用邀请记录替换单一永久通用令牌：

```sql
CREATE TABLE workspace_invites (
  id           TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  token        TEXT NOT NULL UNIQUE,
  email        TEXT NOT NULL DEFAULT '',
  role         TEXT NOT NULL DEFAULT 'guest',
  expires_at   INTEGER NOT NULL DEFAULT 0,
  max_uses     INTEGER NOT NULL DEFAULT 1,
  used_count   INTEGER NOT NULL DEFAULT 0,
  created_by   TEXT NOT NULL REFERENCES users(id),
  revoked_at   INTEGER NOT NULL DEFAULT 0,
  created_at   INTEGER NOT NULL
);
```

规则：

- 管理员可以创建成员或游客邀请。
- 只有所有者可以创建管理员邀请。
- 通用邀请默认角色应为只读的 `guest`。
- 管理员可以将游客调整为成员，也可以将成员降为游客。
- 指定邮箱时必须与当前登录邮箱完整匹配。
- 必须支持过期时间、最大使用次数和主动撤销。
- 一次性邀请的并发消费只能成功一次。
- 邀请加入的用户必须是活跃账号。
- 邀请令牌不能出现在日志、成员或游客接口中。

## 12. 管理员任命

只有所有者可以：

- 将成员或游客提升为管理员。
- 将普通管理员降为成员。
- 移除普通管理员。

普通管理员不能：

- 创建其他管理员。
- 降级其他管理员。
- 移除其他管理员。
- 修改所有者角色。

工作空间至少必须保留一个管理员，且所有者始终满足该条件。

普通管理员可以在 `member` 和 `guest` 之间调整角色，但不能把任何用户提升为 `admin`。

角色变更规则固定为：

```text
所有者：admin <-> member <-> guest（不能修改自己的 admin）
普通管理员：member <-> guest
普通成员：不能修改角色
游客：不能修改角色
```

## 13. 所有权转移

所有权转移必须满足：

- 只能由当前所有者发起。
- 接收者必须是当前工作空间活跃成员。
- 接收者自动成为 `admin`。
- 原所有者默认保留 `admin`。
- 同一事务更新 `workspaces.owner_id` 和成员角色。
- 转移后旧所有者立即失去所有者专属权限。
- 前端要求二次确认，建议输入工作空间名称。
- 操作写入工作空间审计日志。

用户账号删除前：

- 如果仍然拥有工作空间，必须先转移或明确删除。
- 不能因为 `owner_id ON DELETE CASCADE` 意外删除整个团队数据。

## 14. 工作空间模型与工具策略

管理员可以从平台已经存在的能力中选择本工作空间允许使用的范围。

建议配置：

```text
允许的模型
允许的内置工具
允许的 MCP 服务
是否允许 Python 沙盒
是否允许图片生成
是否允许知识库
是否允许文件上传
成员月度额度
```

建议数据：

```sql
CREATE TABLE workspace_policies (
  workspace_id                TEXT PRIMARY KEY REFERENCES workspaces(id) ON DELETE CASCADE,
  allowed_model_ids           TEXT NOT NULL DEFAULT '[]',
  allowed_tool_ids            TEXT NOT NULL DEFAULT '[]',
  allowed_mcp_server_ids      TEXT NOT NULL DEFAULT '[]',
  allow_sandbox               INTEGER NOT NULL DEFAULT 1,
  allow_image_generation      INTEGER NOT NULL DEFAULT 1,
  allow_knowledge_bases       INTEGER NOT NULL DEFAULT 1,
  allow_file_upload           INTEGER NOT NULL DEFAULT 1,
  member_monthly_credit_limit INTEGER NOT NULL DEFAULT 0,
  updated_by                  TEXT NOT NULL DEFAULT '',
  updated_at                  INTEGER NOT NULL
);
```

工作空间策略只能缩小上层允许范围，不能让工作空间成员获得平台没有开放的模型或工具。

游客不参与模型和工具允许列表。即使工作空间策略允许全部模型、工具、MCP 和沙盒，`guest` 仍然不能调用这些能力。

运行工具、MCP、沙盒、图片生成或知识库检索前应重新验证策略，不能只在前端目录加载时检查。

## 15. 工作空间审计日志

建议增加轻量审计日志：

```sql
CREATE TABLE workspace_audit_logs (
  id            TEXT PRIMARY KEY,
  workspace_id  TEXT NOT NULL,
  actor_user_id TEXT NOT NULL,
  action        TEXT NOT NULL,
  target_type   TEXT NOT NULL DEFAULT '',
  target_id     TEXT NOT NULL DEFAULT '',
  metadata      TEXT NOT NULL DEFAULT '{}',

);
```

至少记录：

- 游客加入、退出、升级为成员或被移除。
- 成员提升为管理员。
- 管理员降级为成员或被移除。
- 邀请创建、使用和撤销。
- 资源私有/共享范围变化。
- 工作空间模型、工具、MCP 和额度策略变化。
- 所有权转移。
- 工作空间删除。

审计日志不能保存邀请令牌、API 密钥、完整请求体或敏感文档内容。

## 17. 数据迁移

### 17.1 角色迁移

```text
现有 owner -> admin，并保留 workspaces.owner_id
现有 member -> member
新游客邀请或角色调整 -> guest
```

迁移期间可以兼容读取旧 `owner`，但新数据只写入 `admin/member/guest`。现有成员不能自动降级为游客。

### 17.2 成员能力迁移

第一阶段不要直接删除现有权限列。

建议：

1. 授权器读取新角色和旧成员能力列。
2. 将旧 `can_delete_kb_content` 收紧为不能删除他人内容。
3. 新接口返回规范化有效权限。
4. 前端切换到新权限语义。
5. 稳定后再决定是否重建旧字段。

### 17.3 资源范围迁移

迁移必须保持已有用户可见范围：

- 不能把原共享项目迁移成私有。
- 不能把原共享知识库迁移成私有。
- 不能把原私有对话迁移成共享。
- 文件、文档、向量、引用和沙盒产物必须继续可访问。

## 18. 实时撤权

以下变化必须立即生效：

- 成员被移除。
- 成员退出。
- 管理员被降级。
- 管理员被移除。
- 成员被降级为游客。
- 游客被移除。
- 资源从共享改为私有。
- 工作空间模型或工具策略变化。
- 所有权转移。

建议权限版本：

```text
workspace:permission-epoch:{workspace_id}
workspace:member-epoch:{workspace_id}:{user_id}
```

需要继续复用现有缓存事件、生成终止和工作空间 mutation 锁。

不能只通知前端刷新；后端运行中的任务必须在工具调用、文件访问、知识库检索和最终写入前重新验证关键权限。

## 19. 测试清单

### 角色

- 创建者自动成为所有者和管理员。
- 所有者不能被降级、移除或直接退出。
- 所有者可以提升或降级普通管理员。
- 普通管理员可以管理普通成员。
- 普通管理员可以在成员和游客之间调整角色。
- 普通管理员不能管理其他管理员。
- 成员不能访问管理员接口。
- 游客不能访问管理员接口。
- 游客不能通过直接 API 调用执行任何 mutation。
- 游客不能调用模型、RAG、工具、MCP、沙盒或图片生成。

### 工作空间隔离

- 工作空间 A 成员不能访问工作空间 B 资源。
- 同一用户加入多个工作空间时数据不会混合。
- 切换工作空间时旧请求结果不会写入新工作空间状态。
- 直接资源 ID 不能绕过工作空间成员检查。
- 文件、RAG、引用、沙盒和工具路径不能跨工作空间。

### 对话

- 私有对话只有创建者和管理员可见。
- 共享对话允许当前工作空间成员参与。
- 游客可以查看共享对话，但不能继续发送消息。
- 成员不能修改其他成员对话元数据。
- 成员只能删除自己的轮次。
- 删除分支不能删除其他成员内容。
- 成员被移除后进行中的生成被终止。

### 项目

- 私有项目只有创建者和管理员可见。
- 共享项目允许工作空间成员使用。
- 游客可以查看共享项目，但不能创建对话、上传或修改项目。
- 成员不能修改其他成员创建的项目。
- 项目创建者和管理员可以删除项目。
- 项目文件继承项目权限。

### 知识库

- 私有知识库只有创建者和管理员可见。
- 共享知识库允许工作空间成员检索和附加。
- 游客可以查看共享知识库和已有文档，但不能发起 RAG、附加到对话或上传内容。
- 成员只能删除自己上传的文档。
- 知识库创建者和管理员可以管理全部文档。
- RAG 检索不能跨工作空间或绕过私有范围。
- 文件预览和引用不能绕过知识库范围。

### 邀请

- 指定邮箱必须完整匹配。
- 过期邀请无法使用。
- 撤销邀请无法使用。
- 一次性邀请并发请求只成功一次。
- 普通管理员不能创建管理员邀请。
- 通用邀请默认创建游客。

### 所有权

- 只有所有者可以转移所有权。
- 接收人必须是当前成员。
- 新所有者自动成为管理员。
- 旧所有者立即失去所有者专属操作。
- 拥有工作空间的账号不能直接触发意外级联删除。
