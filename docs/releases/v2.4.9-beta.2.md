# Aivory v2.4.9-beta.2

> Test release / prerelease. This is not a stable production release.

`v2.4.9-beta.2` is the second focused test build in the 2.4.9 line. It adds prerelease-aware in-app updates and public HTML preview links. Back up application data before testing and use a staging deployment where possible.

## What to test

### Stable and test release updates

- The administrator **System update** dialog now lists the newest stable release and newest GitHub prerelease separately.
- Administrators can select and install a newer beta or release-candidate build from the dialog.
- A prerelease by itself does not enable the sidebar update badge. The badge remains reserved for a newer stable release.
- Release installation is restricted to a version currently returned by the configured GitHub release source; arbitrary image tags remain rejected.
- Semantic-version ordering handles prereleases correctly, including `beta.2` after `beta.1` and a final release after its beta or release candidate.

### Public HTML previews

- Completed assistant HTML code blocks expose a link icon in both the code toolbar and the right-side preview header.
- Selecting the icon creates and copies a public preview URL. Anyone with the URL can open the rendered result without signing in.
- The public response contains the preview document only, with no Aivory application shell, code viewer, or explanatory text.
- Public preview documents run under a CSP sandbox with an opaque origin and cannot read Aivory cookies, storage, or application DOM.
- Generated Tailwind utility markup uses a stable runtime URL so shared previews remain renderable across application asset-hash changes.
- Creating and opening previews follows the publisher's current user-group sharing permission. Revoking sharing makes existing links unavailable.

## Upgrade and deployment

The updater included with `v2.4.9-beta.1` only accepts stable image tags. Therefore the one-time move from beta.1 to beta.2 must update both the application and updater containers outside the old in-app updater:

```dotenv
APP_IMAGE_TAG=2.4.9-beta.2
UPDATER_IMAGE_TAG=2.4.9-beta.2
```

Then pull and recreate the two services using the deployment's existing Compose file:

```bash
docker compose -f docker-compose.prod.yml pull app updater
docker compose -f docker-compose.prod.yml up -d --no-deps --force-recreate updater app
```

After beta.2 is running, its updater accepts strict prerelease tags and the System update dialog can install later published beta or release-candidate builds.

Do not replace an existing deployment environment file with an example. Preserve the existing Compose project name, data paths, database credentials, host ports, and secrets.
