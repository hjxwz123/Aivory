## What's Changed

Aivory 2.4.8 is the workspace governance and administration release. It adds enterprise email-domain enrollment, workspace announcements and usage statistics, consistent permission boundaries, and administrator-initiated Docker updates. Generated images gain mask-based editing, conversation organization gains bulk archive and complete history cleanup, and passkey login, historical backup restoration, and retrieval timeout handling receive reliability fixes. Workspace management now follows the user settings layout, with bounded dialogs and a single scrolling content area.

### Workspace management, announcements, and statistics

- Redesigns workspace management around the user settings layout: a left navigation rail and right content pane on desktop, and a full-screen dialog with horizontal navigation on small screens.
- Groups management into Members, Invites, Capabilities, Announcement, Audit, and Statistics. Ordinary members continue to see only the member information available to their role.
- Keeps section headings and footer actions visible while the content scrolls. Member, invitation, and audit lists share the main content scroller, eliminating nested vertical scrollbars. Switching sections resets the scroll position; arrow keys and Home / End support keyboard navigation.
- Lets workspace owners and administrators publish announcements visible only to their workspace, with rich text, images, modal and banner presentation, remembered dismissal, and an optional required-reading countdown.
- Keeps workspace and site-wide announcement configuration separate. Modal and banner dismissals track their own revisions; announcement updates notify connected clients and create workspace audit entries.
- Adds usage statistics for the last 24 hours, 7 days, 30 days, 90 days, and 365 days, including conversation rounds, request counts, input/output tokens, active members, credits, provider cost, per-member usage, and comparisons with the previous period.
- Restricts statistics to managers of the current workspace. Access to usage statistics does not grant access to other members' private conversation contents.

### User-group and workspace permission boundaries

- Applies system user-group permissions, workspace-wide switches, ordinary member permissions, and resource access rules together. A denial at any applicable layer prevents the operation; workspace access cannot override a system user-group restriction.
- Adds user-group switches for prompts, skills, and workspace deletion, and completes permission checks across personal resources, workspace resources, catalog queries, and runtime invocation.
- Allows workspace owners and administrators to bypass ordinary member-level restrictions while still respecting user-group and workspace-wide limits. System administrators retain their user-group exemption but remain subject to workspace-wide switches.
- Separates permission to delete an entire workspace from permission to delete messages, conversations, or conversations within a project.
- Fixes knowledge-base creators bypassing member or resource content permissions. Resource administration and permission to upload or delete content are evaluated separately.
- Checks knowledge-base details, file reads and management, member settings, project materials, attachment transfers, and automatic ingestion against the workspace that actually owns the resource.
- Validates user-group, workspace, member, and knowledge-base upload permissions before enabling a project's automatic knowledge-base ingestion. Denied changes are not saved; users can still disable an existing setting after access is revoked.
- Allows ordinary conversation attachments to upload when permitted even if the workspace has disabled knowledge bases, while preventing those attachments from being automatically ingested into a project knowledge base.
- Aligns MCP invocation, connection tests, tool synchronization, and model fallback with the same permission boundaries. Adds self-hosted MCP service grants and fixes the frontend hiding valid actions granted through the `usermcp:*` wildcard.
- Adds a prominent domain-management explanation of the permission intersection, recommending that default user groups allow the intended capabilities before workspaces narrow access. Existing group configuration is not changed automatically.
- Constrains the Add / Edit Domain dialog to the viewport and gives only the form body a vertical scrollbar, keeping Cancel and Save visible.

### Private chat permissions

- Adds private-chat controls to both system user groups and workspaces. Both applicable switches must allow access; guests cannot start private chats.
- Stops hiding private chat unconditionally for enterprise-domain accounts with a locked personal space. These users can use private chat within their assigned workspace when its effective permissions allow it.
- Uses consistent permission checks for the entry point, page, and send action. Permission refreshes retain the current in-memory conversation while temporarily preventing sends.
- Rechecks workspace access, allowed models, image-upload permissions, and member monthly quotas on the server. Locked accounts that omit the workspace parameter use their assigned workspace; requests targeting another workspace are rejected.
- Reacts to permission revocation during active private requests. Workspace usage records include only the attribution needed for statistics, without creating ordinary conversation history or persisting private message bodies.
- Enables the new workspace private-chat switch by default for compatibility. Private chat remains distinct from the “visible only to me” setting on an ordinary conversation.

### Enterprise email-domain enrollment

- Lets system administrators assign a workspace and initial user group per email domain, enable or pause automatic enrollment, require email verification for password registration, and lock access to the personal space.
- Evaluates password-registration verification against both the global setting and the matching active domain rule. Verification is required if either requires it; registration proceeds without a code when both are disabled.
- Applies matching domain enrollment, initial-group assignment, and personal-space restrictions to new third-party and generic OAuth2 accounts as well. Federated login does not add a separate Aivory email-code challenge.
- Matches the exact email domain rather than implicitly including subdomains. Account creation, domain binding, and workspace membership are committed in one transaction.
- Enforces personal-space locking in both the interface and the API, including workspace switching, personal resource access, invitations, joining, and leaving workspaces. Administrators can configure user-specific exceptions.
- Pausing a rule stops subsequent automatic enrollment. Deleting a rule removes its bindings and restrictions while preserving existing memberships and data; existing accounts are not retroactively enrolled.
- Supports administrator-created workspaces with an assigned owner and ownership transfers to an existing member.

### Mask-based image editing

- Adds an Edit action to generated images for supported OpenAI-format image models. Users can paint the region to change and submit an editing instruction with the original image and a PNG mask.
- Provides brush and eraser tools, adjustable brush size, undo / redo, clear, and selection preview.
- Binds source images and masks to the relevant message round and preserves editing parameters through message edits, retries, and regeneration.
- Validates image and mask access, conversation and branch ownership, image formats, and dimensions on the server to reject cross-conversation references and invalid edit requests.
- Refines the image editor, canvas toolbar, and in-progress drawing state, including small-screen layout and reduced-motion preferences.
- Requires an upstream model and channel that support image editing. Text-to-image-only models do not gain editing support through this feature; DALL·E 3 is excluded.

### Conversation organization and project actions

- Fixes Clear All Conversations in Privacy & Data deleting only the portion loaded by the frontend. The server processes the current account's complete personal history in batches, including archived conversations.
- Adds Archive All for all unarchived top-level personal conversations, independent of sidebar pagination.
- Keeps personal-history cleanup and archival scoped to personal conversations; workspace-shared conversations are not changed, and inline threads follow their parent conversations.
- Bounds the archived-conversations dialog to the viewport, improves its scrolling behavior, and removes misleading simulated-action copy.
- Replaces sidebar project counts with a three-dot action menu shared with the project detail page.
- Adds an option to delete all conversations when deleting a project. Leaving it unchecked preserves the conversations and moves them out of the project; conversation deletion still requires the relevant permissions.

### Passkey login and backup restoration

- Fixes `Backup Eligible flag inconsistency detected during login validation` by persisting and restoring authenticator backup-eligibility and backup-state flags.
- Initializes missing flags on legacy credentials only after signature, challenge, origin, RP ID, and identity validation succeed. Credentials with known flags continue to enforce backup-eligibility consistency.
- Counts only actual verification failures against login challenges and consumes successful challenges once. Server diagnostics retain the specific failure while the client receives a generic login error.
- Improves origin-configuration errors and the account-page passkey controls, with end-to-end registration and login regression coverage using a software authenticator.
- Restores historical v3 backups using their original schema and the current foreign-key dependency order. Invalid or damaged backups are rejected before target data is changed.
- Preserves the current administrator's valid passkeys and device-side user handles across account-ID changes during restoration, and rolls back on credential conflicts.
- Preserves target skill assets during configuration import and includes workspace announcements and domain rules in full backups.

### Retrieval and runtime reliability

- Preserves completed retrieval results as partial evidence when the evidence-sufficiency judge times out independently and the overall request is still valid.
- Continues to return errors for request cancellation, overall timeout, billing write failures, or the absence of usable evidence instead of treating those cases as successful retrieval.
- Reduces repetitive per-turn generation-stage and routing-model logs while retaining failure diagnostics.

### Administrator updates

- Adds a current-version badge below the administrator entry in the sidebar and highlights it when a newer stable GitHub Release is available.
- Shows the installed and latest versions, publication date, complete release notes, and an update action. Long release notes use a single scrolling region.
- Introduces an internal Docker updater service that pulls the selected application version, writes `APP_IMAGE_TAG`, recreates only `app`, and waits for its health check.
- Persists update jobs and attempts to restore the previous application image configuration if recreation or health checks fail. Image rollback is not a substitute for database restoration.
- Publishes no updater host port and authenticates through an automatically generated credential in the shared data directory. The administration endpoint accepts the latest stable semantic release version rather than arbitrary images or Docker commands.
- Keeps routine in-app updates scoped to the application image. The updater itself and sandbox images remain managed through Compose.

### Verification

- All 668 frontend tests across 120 test files pass, along with TypeScript checking and the production build.
- The complete Go test suite and all five updater tests pass. Corrects the automatic-ingestion regression fixture so a readable but non-writable knowledge base reaches the intended permission-denial check.
- Validates both updated dialogs in a browser at desktop, tablet, phone, and landscape sizes without screenshots: viewport containment, a single content scroller, stable footer actions, keyboard section switching, and domain dropdown interaction.

### Upgrade notes

- Database migrations run automatically on application startup for SQLite and PostgreSQL. Back up the database, uploaded files, and generated artifacts before upgrading; recreating the application briefly interrupts service.
- All four release images support `linux/amd64` and `linux/arm64`:

  ```text
  ghcr.io/hjxwz123/aivory-app:2.4.8
  ghcr.io/hjxwz123/aivory-updater:2.4.8
  ghcr.io/hjxwz123/aivory-sandbox:2.4.8
  ghcr.io/hjxwz123/aivory-sandbox-sidecar:2.4.8
  ```

**Deployments with the updater already configured** can use the sidebar version badge. To update manually, set `APP_IMAGE_TAG=2.4.8` in the existing deployment's `.env`, then run from that deployment directory:

```bash
docker compose -f docker-compose.prod.yml pull app
docker compose -f docker-compose.prod.yml up -d --no-deps --no-build app
docker compose -f docker-compose.prod.yml ps app
```

**Older deployments without the updater** need one manual configuration update. Merge the new Compose file's `updater` service, `update-state` volume, and application updater environment variables into the existing configuration. The application image tag should use `${APP_IMAGE_TAG:-${IMAGE_TAG:-latest}}`. Pulling `app` alone does not create an updater service.

Preserve the original deployment directory, Compose project name, `.env`, host ports, data paths, database credentials, and JWT secret. The repository example uses `80:8787`; deployments using `8082:8787` or another custom mapping should keep their existing port. Do not replace the existing environment file with an example file or run `down -v`.

Set the following in the existing `.env`:

```dotenv
APP_IMAGE_TAG=2.4.8
UPDATER_IMAGE_TAG=2.4.8
```

Existing `IMAGE_TAG` and `SANDBOX_IMAGE_TAG` values can remain unchanged; upgrading the application does not require changing the sandbox version. Then run:

```bash
docker compose -f docker-compose.prod.yml config --quiet
docker compose -f docker-compose.prod.yml pull app updater
docker compose -f docker-compose.prod.yml up -d --no-deps --no-build updater app
docker compose -f docker-compose.prod.yml ps app updater
docker compose -f docker-compose.prod.yml logs --tail=100 app updater
```

For the personal stack, replace the Compose arguments in each command with `--env-file .env.personal -f docker-compose.personal.yml` and put the version variables in the existing `.env.personal`. Deployments that use `-p` must retain the same project name and configure the updater's internal Compose operations to use it as well.

The in-app update check follows stable Releases rather than every `main` commit. Instances previously running development commits through `latest` should pull the formal 2.4.8 image even if their interface still reports 2.4.7.
