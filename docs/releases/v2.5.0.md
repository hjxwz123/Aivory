# Aivory v2.5.0

`v2.5.0` is the stable release of the 2.5 series. This summary covers changes since `v2.4.0`, including the intervening 2.4.x releases and the finalized 2.5.0 beta work.

## From chat to finished files

- A unified, resizable artifact panel opens HTML, conversation files, sandbox outputs, generated files, and knowledge-base documents beside the conversation. It also works as a mobile sheet.
- Browser editors support text, code, HTML, DOCX, XLSX, and existing PPTX text. Edited results can be downloaded or saved as new file copies. PPTX editing does not add or redesign slide objects; XLSX editing supports a bounded grid and a subset of formulas.
- Conversation folder upload preserves relative paths for sandbox tasks. The Files page displays folders as folders, and the sandbox can read their nested contents. Folder upload needs an enabled sandbox and the relevant file and tool permissions.
- Conversations gained queued follow-ups, more reliable branch switching and stop handling, bulk archive actions, private chats, and clearer actions for editing, forking, regenerating, and deleting messages. A stopped opening reply can be deleted and its question can be edited and resent.

## AI PPT and multimodal work

- The optional AI PPT workbench creates and manages presentations through Aivory's own UI and the server-side Docmee API. Users can edit outlines, choose templates, preview decks, and save presentations; administrators manage integration settings under **Capabilities & integrations > AI PPT**.
- Generation and paid edits use the existing credit ledger and appear in usage records. Access is subject to user-group and workspace permissions. The workbench requires an enabled Docmee integration; it is not a built-in, keyless presentation model.
- An optional administrator-selected vision model can describe attached images for text-only conversation models. Native vision models still receive images directly; vision reads may add latency and model cost.
- Generated files can be previewed directly from chat, alongside their download action.

## Search and model decisions

- Web search now offers Tavily and an explicit, keyless DuckDuckGo backend in addition to the existing providers. DuckDuckGo's public endpoints can challenge or throttle server IPs; use a configured provider where predictable availability matters.
- Search-only and automatic tool routing choose a smaller tool set for focused searches while keeping the full tool set for complex work. Optional TypeSafe/Jev policies can drive tool routing, memory decisions, moderation, and document-use decisions after an administrator configures a channel and policy.
- Public, sandboxed HTML preview links let a recipient inspect a completed HTML artifact without signing in, subject to the publisher's current sharing permission.
- Response replay, tool-call limits, context handling, and document retrieval received reliability fixes across the 2.4.x releases.

## Teams, administration, and sign-in

- Workspace and domain controls gained email-domain enrollment, announcements, usage statistics, profile management, personal-data resolution, and more explicit capability and deletion permissions.
- The administrator can update the application from a published stable release. The update controller changes the app image; updater and sandbox images still need to be managed with Compose.
- Optional passkeys and WeCom sign-in join the existing authentication methods. Login, registration, recovery, and first-run screens received a responsive redesign.
- The app, updater, sandbox runner, and sandbox sidecar publish multi-platform images for `linux/amd64` and `linux/arm64`.

## Upgrade

Back up the database, uploaded files, and generated artifacts before upgrading. Preserve the existing deployment directory, Compose project name, `.env`, secrets, ports, and data paths. Database migrations run on application startup. AI PPT, TypeSafe, DuckDuckGo, vision captioning, and sandbox folder tasks remain optional and require their respective configuration or permissions.

For a full-stack installation using `deploy/docker-compose.prod.yml`, set these values in the deployment's actual `deploy/.env` after all four images are published:

```dotenv
IMAGE_TAG=2.5.0
UPDATER_IMAGE_TAG=2.5.0
```

Remove or align explicit `APP_IMAGE_TAG` and `SANDBOX_IMAGE_TAG` overrides so they do not select older images. Then check the resolved images before pulling and starting:

```bash
cd deploy
docker compose --env-file .env -f docker-compose.prod.yml config --images
docker compose --env-file .env -f docker-compose.prod.yml pull
docker compose --env-file .env -f docker-compose.prod.yml up -d --no-build
```

Personal-profile deployments should keep their existing `docker-compose.personal.yml` and `.env.personal` configuration and follow the corresponding instructions in `deploy/README.zh-CN.md`.
